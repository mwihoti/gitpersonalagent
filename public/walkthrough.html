How it works

Working on Bitcoin issues

DanAgent checks Bitcoin repositories for open issues and helps you decide where to start. Use the dashboard or Telegram to review the discussion, see whether someone is already working on an issue, and track your pull request.

01

Choose a project

Browse node software, Lightning, wallets, privacy tools, and other Bitcoin projects. Choose an area below to narrow the directory.

Experience labels describe how much Bitcoin knowledge a project usually needs. The scope of individual issues varies.

A familiar language is a useful starting point. Read the project’s contribution guide and a few recent issues to see whether the work fits your experience.

Add a project to your watchlist on the dashboard to include it in future scans. You can also add a GitHub repository that isn’t in this directory.

Project directory
02

Run a scan

Click Run scan on the dashboard. You can start with an empty watchlist or add the repositories you want to follow.

Scans check your watchlist first. With an empty watchlist, they use the BitcoinDevs good-first-issue board. If the board is unavailable or empty, they check projects from the directory.

If you host DanAgent yourself, set BITCOIN_FOCUS_AREAS and PREFERRED_LANGUAGES to give matching issues more weight. Other issues can still appear.

# repository sources, in order $ watchlist → repos you added yourself $ bitcoindevs.xyz → the good-first-issue board $ catalogue → 42 curated repos, 11 areas # optional preferences in your .env file $ BITCOIN_FOCUS_AREAS=lightning,privacy $ PREFERRED_LANGUAGES=Rust,TypeScript
Empty results? A scan may find no new issues. Check your watchlist and the scan history before running it again.
03

Review what changed

The daily digest groups new issues, recent updates, and issues that have closed or been claimed. Unchanged recommendations are left out.

DanAgent checks for assignees, open pull requests that reference the issue, and comments such as “I’ll pick this up.”

By default, a claim expires after 45 days without a pull request. The issue can appear again with a stale-claim note. Ask in the thread whether it’s still available before starting.

Check the latest discussion before you start; the issue may have changed since the last scan.

04

Read the issue analysis

Click Analyze issue to review the discussion, linked pull requests, contribution guide, and referenced source files. The result includes the issue’s status, suggested changes, and a plan.

State

Is the issue available?

available start

No assignee, open pull request, or recent claim was found.

claimed stop

Someone recently said they are working on it. Check with them.

has_open_pr stop

A pull request references this issue. Check what it covers.

likely_done stop

A merged pull request may have resolved the issue.

stale ask

An older claim has no linked pull request. Ask whether it’s available.

needs_design ask

The approach is still under discussion. Ask what needs deciding.

needs_clarification ask

The requirements need clarification. Ask in the issue thread.

blocked wait

Progress depends on other work. Check the dependency.

The analysis includes quotes from the discussion, files to investigate, suggested steps, test commands, and open questions. Review these alongside the original issue.

A checkmark beside a file means its path was verified in the repository. Other paths are suggestions from the model. Review the analysis before saving the plan or writing code.

06

Keep track of your pull request

Select I’ll take it in Telegram, or set an issue to In progress on the dashboard. Link your pull request once it’s open.

Scans check linked pull requests for reviews, test failures, conflicts, and merges. The digest’s Your work section lists items that need your attention first.

A merged pull request marks the issue as done. Taking, finishing, or dismissing issues also helps rank future suggestions. When you dismiss an issue in Telegram, you can give a reason.

# claim it, from the digest message › [ I'll take it ] → In Progress, owner: you # link the PR once it is open $ /pr <issue url> <pr url> › Linked. I will track it for reviews, CI, and merge. # set GITHUB_LOGINS and this happens by itself $ GITHUB_LOGINS=your-handle
Automatic tracking. If you host DanAgent yourself, set GITHUB_LOGINS to link your pull requests to tracked issues automatically.
